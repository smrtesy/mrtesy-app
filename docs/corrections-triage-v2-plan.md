# תוכנית — מיון-תיקונים v2: הבנה → סיווג → בדיקה → תיקון, עם דיווח מסודר

מסמך לאישור. אין בו קוד — רק העיצוב, מעוגן בקוד הקיים. אחרי אישור אכתוב את
המימוש.

## המטרה

היום מיון-התיקונים **מסווג ומתריע** — ונעצר. תיקון שסווג כ"ממשק" או "קוד" מגיע
כהתראה ואף אחד לא מבצע אותו; והמשתמש לא תמיד מבין מההתראה מה בעצם קרה. v2 הופך
את התהליך למלא: הבנה → סיווג → בדיקה מול היסטוריה → **הצעת תיקון → אישור →
ביצוע**, עם התראה שהיא דו"ח מסודר וכפתור לחזור לשיחה.

הכל רץ על **המנוי** (Claude Code CLI דרך `CLAUDE_CODE_OAUTH_TOKEN`) — **אפס
עלות API**. ה-runner מסיר `ANTHROPIC_API_KEY` מהסביבה כדי שלא ידלוף לנתיב מחויב
(`server/src/modules/claude/runner.ts`).

## המצב היום (מעוגן בקוד)

- `server/src/modules/smrttask/corrections/triage.ts` — קורא ל-`runOneShot`
  (טקסט בלבד), מסווג ל-`prompt / code / ui / duplicate / unclear`, ומתריע.
  **אין** שער-הבנה, **אין** בדיקה מול ה-golden set, ההתראה היא גוף חופשי ולא
  דו"ח מסודר, **אין** לינק חזרה לשיחה.
- אישור: כלל-פרומפט נכנס לסיווג רק כש-`context.triage.approved = true`
  **וגם** `prompt_class = "prompt"` (allow-list). כלומר תשתית האישור כבר קיימת.
- **התשתית לביצוע כבר בנויה:** `runner.ts` הוא מנוע Claude Code מלא — `executeRun`
  משכפל את הריפו (`ensureClone`), יש לו טוקן GitHub (`getGitHubToken`), ורץ על
  המנוי. `runOneShot` הוא רק הנתיב הטקסטואלי של אותו מנוע.
- **threads = שיחות שאפשר לחזור אליהן:** `server/src/modules/claude/threads.ts`
  — כל thread מחזיק את session-id של המנוע, וכל תור נוסף **מתחדש** לתוכו. REST
  מלא (`POST /api/claude/threads`, `/threads/:id/messages`…). זה יעד הלינק.
- **ה-golden set:** `classifier_golden_set` (206 שורות, 163 מתויגות) +
  `classifier_quality_metrics` — קורפוס אמיתי שכל שינוי פרומפט/מודל נמדד מולו.
  התוויות מגיעות מפעולות שהמשתמש **עשה**, לעולם לא ממודל.

## הזרימה החדשה — שער מדורג

התיקון מגיע עם **כל המידע המובנה** (ID המשימה, ההודעה, הלינקים המלאים) ונמסר
ל-Claude. כל שלב יכול לעצור, ואם אין ודאות — לשאול במקום לנחש.

### שלב 1 — הבנה (חדש)
לפני כל דבר אחר, Claude מנסח **במילותיו** מה התיקון מבקש. אם ההבנה לא ודאית →
עוצר, מסווג את המצב כ-`needs_question`, ומחזיר **שאלה** למשתמש (בהתראה + לינק
לענות). זהו שער נפרד וראשון — הבנה היא תנאי מוקדם לסמוך על כל מה שבא אחריו.

### שלב 2 — סיווג
`prompt` / `code` / `ui` (+ `duplicate` / `unclear` כמו היום).

### שלב 3 — בדיקה מול היסטוריה
- **כלל-פרומפט:** מריץ את הכלל המוצע מול ה-`classifier_golden_set` ומודד מול
  `classifier_quality_metrics` — האם הוא תופס את המקרים הנכונים **בלי לשבור**
  שורות מתויגות. זו הבדיקה שמונעת "כלל שנשמע טוב" מלהזיק (בדיוק הבעיה ש-CLAUDE.md
  מתעד: כל תיקון-פרומפט היסטורי לא באמת עבד).
- **קוד / ממשק:** ה-golden set לא רלוונטי; הבדיקה היא **פרוטוקול קדם-הדחיפה**
  (build + greps + סקירת סוכן) בתוך סשן הביצוע.

### שלב 4 — הצעת תיקון → אישור → ביצוע

**עיקרון-על: המשתמש מאשר מה התיקון עושה, לא איך הקוד נראה.** המשתמש לא קורא קוד,
ולכן **לעולם לא מוצג לו diff.** הנכונות הטכנית (build, golden set, סקירת סוכן) היא
עבודת השערים האוטומטיים. תפקיד המשתמש: לאשר שהבנתי נכון מה הוא רצה ושהתוצאה נכונה —
בעברית או בעיניים. (החלטה #5.)

1. **מציע** — Claude מנסח את התיקון **בעברית פשוטה**: מה היה שבור / לא ברור, ומה
   ישתנה. לא נוסח קוד.
2. **אישור — לפי סוג, אף פעם לא diff:**
   - **ממשק:** **לינק תצוגה מקדימה חיה** (Vercel Preview של ה-PR). המשתמש לוחץ,
     **רואה את המסך החדש**, ואומר "כן" / "לא, התכוונתי אחרת".
   - **כלל-פרומפט:** הסבר במילים + **מה הכלל היה עושה על הודעות עבר** מה-golden set
     ("היה ממיין נכון את 5 אלה, לא היה שובר אף אחת").
   - **לוגיקה בצד השרת:** הסבר בעברית של הבעיה והתוצאה ("חזר כי X → התיקון גורם ל-Y").
   שום דבר לא מוחל אוטומטית. (החלטה #2.)
3. **ביצוע** — אחרי אישור:
   - **פרומפט:** הכלל נכנס לפרומפט הסיווג (`approved = true`). **ללא PR** — זה
     שינוי נתונים מאומת מול ה-golden set. (החלטה #6.)
   - **קוד / ממשק:** נפתח **סשן Claude אמיתי** (`executeRun`, עם שכפול הריפו),
     שמיישם, מריץ את פרוטוקול קדם-הדחיפה, ופותח **PR** שמתמזג אחרי האישור. ה-PR
     וה-diff הם הרשומה הטכנית והשער — **מאחורי הקלעים; המשתמש לא רואה אותם.**
     (החלטות #3 + #6.)

## מה זה "תיקון" לכל סיווג

| סיווג | מה המשתמש רואה לאישור | בדיקה (אוטומטית) | ביצוע אחרי אישור |
|---|---|---|---|
| `prompt` | הסבר + דוגמאות עבר מה-golden set | golden set | הכלל נכנס לפרומפט (ללא PR) |
| `code` | הסבר בעברית של הבעיה והתוצאה | פרוטוקול קדם-דחיפה | סשן Claude מיישם → PR מאחורי הקלעים |
| `ui` | **תצוגה מקדימה חיה** (Vercel Preview) | build + סקירה | סשן Claude מיישם → PR מאחורי הקלעים |
| `duplicate` | ההסבר שזה כפילות | — | מקושר לתיקון הקיים |
| `needs_question` | השאלה בעברית | — | ממתין לתשובתך בלינק |

## ההתראה — דו"ח מסודר

- **כותרת:** `<ID> · <סטטוס>` — הסטטוס אחד מ: *בדק ומצא* / *בדק ויש שאלה* /
  *תוקן* / *ממתין לאישור*.
- **גוף, שלב-שלב:** בדקתי, הבנתי → סיווגתי כ-X → מצאתי את מקור הבעיה → זה התיקון
  / זה מה שתוקן. (אם `needs_question` — השאלה במקום זה.)
- **כפתור** שמחזיר ל**שיחת Claude אמיתית** (thread) — להמשיך לחפור, או לענות על
  השאלה ולהמשיך. (החלטות #2 + #4.)

**מסך האישור עצמו — לא diff:** מה התיקון עושה בעברית + תצוגה מקדימה חיה (ממשק) או
דוגמאות עבר (פרומפט), וכפתורי **"כן, בצע"** / **"לא, זה לא זה"**. ה-PR/diff נשארים
מאחורי הקלעים כרשומה וכשער. (החלטה #5.)

## הלינק — חזרה לשיחה

התיקון מעובד בתוך **thread** (`claude/threads.ts`). ההתראה מקשרת אליו (בדפוס
ה-deep-link הקיים לסשן). לחיצה → אתה בשיחה עם אותו Claude, עם כל ההקשר, לענות או
להמשיך. אין "צ'אט קליל" נפרד — זו שיחת המנוע עצמה.

## מעקות בטיחות ועלות

- **fail-closed:** שלב שנכשל משאיר את התיקון לא-מוחל (לא מגיע לפרומפט), רועש בלוג,
  לעולם לא פוגע בבקשה — כמו היום.
- **הבדיקה היא שער חובה:** כלל-פרומפט לא עובר בלי golden set; קוד/ממשק לא נדחף בלי
  פרוטוקול קדם-הדחיפה (זה שתפס 7 תיקונים חלקיים שלי בסשן הזה).
- **אישור אנושי לפני כל שינוי** (החלטה #2) — כולל שינוי קוד לפרודקשן.
- **עלות:** הכל על המנוי. אפס טוקני API. לא כפוף לאישור-עלות.

## ההחלטות שננעלו

1. שער-הבנה = שלב ראשון נפרד. ✓
2. שום דבר לא מוחל אוטומטית — אישור בהתראה דרך הלינק. ✓
3. Claude **מבצע** את התיקון (כולל קוד) אחרי אישור, לא רק מתריע. ✓
4. יעד הלינק = שיחת Claude אמיתית (thread). ✓
5. **המשתמש מאשר מה התיקון עושה — עברית + תצוגה מקדימה — לעולם לא diff.** ✓
6. **קוד/ממשק דרך PR (מאחורי הקלעים); כלל-פרומפט ללא PR.** ✓

## שלבי מימוש (אחרי אישור התוכנית)

1. **שער-הבנה + סיווג** ב-`triage.ts` — שלב `needs_question`, פורמט תשובה מובנה.
2. **בדיקת golden set** לכלל-פרומפט — הרצה מול הקורפוס ומדד עובר/נכשל.
3. **ההתראה המובנית** — כותרת ID+סטטוס, גוף שלב-שלב, כפתור לינק ל-thread.
4. **גשר הביצוע** — פתיחת thread/`executeRun` לקוד/ממשק אחרי אישור, כולל פרוטוקול
   קדם-הדחיפה.
5. **מסך האישור** — הלינק פותח את ה-thread עם ההצעה וכפתור "אשר" שמפעיל את הביצוע.

## שאלות פתוחות (לא חוסמות — להכרעה במימוש)

- **מתי נפתח ה-thread** — כבר בשלב ההבנה (כדי שהשאלה תהיה חלק מהשיחה) או רק בביצוע.
  הצעתי: כבר בהבנה, כך שהלינק תמיד מצביע על שיחה חיה.
- **תצוגה מקדימה לשינוי ממשק** — ה-Vercel Preview של ה-PR נותן לינק חי; צריך לוודא
  שהלינק מגיע ל**מסך הנכון** (למשל הנכנס עם משימה מושלמת) ולא לדף הבית, לפי עקרון
  ה-deep-link של CLAUDE.md.

**הוכרע:** קוד/ממשק דרך PR מאחורי הקלעים; אישור לפי תצוגה מקדימה/הסבר, לא diff
(החלטות #5–#6).
