# תכנון: Claude כמנוע בתוך smrtesy

> **המטרה:** ש-Claude יהיה **חלק מהתוכנה שלנו** — לא כלי חיצוני שיוצאים אליו.
> הנתונים אצלנו, הממשק שלנו, ההפעלה מתוך האפליקציה, האוטומציה שלנו.
> הכל על **מנוי Claude Team — אפס טוקני API בתשלום.**

בדיקת ההיתכנות שקדמה: [`feasibility.md`](./feasibility.md).

---

## 1. מה זה אומר בפועל

Anthropic מספקת את המנוע כ**ספרייה** (`@anthropic-ai/claude-agent-sdk`) —
אותו מנוע שמריץ את Claude Code, אבל כרכיב בתוך הקוד שלנו. אין טרמינל, אין
claude.ai, אין "כלי שקוראים לו מבחוץ".

**מה באמת שלנו:**

| | |
|---|---|
| **הנתונים** | כל הרצה, כל התמלול, כל תוצר — ב-Supabase שלנו. **המקור**, לא עותק. |
| **הממשק** | המסך שלנו. המשתמש לא רואה מוצר של Anthropic. |
| **האוטומציה** | כפתור, שורה שנכנסה ל-DB, webhook, שעה קבועה, סיום עבודה קודמת. |
| **השליטה** | אנחנו מגדירים אילו כלים יש לו, במה מותר לגעת, מה דורש אישור. |

**הגבול היחיד, ביושר:** החשיבה עצמה קורית בשרתי Anthropic, וצריך מכונה שתריץ
את התהליך. אין דרך ש-Claude "יֵשֵׁב" פיזית אצלנו. זו עובדה של המוצר.

## 2. מה כבר קיים — בונים על זה

הצנרת כבר עובדת בפרודקשן, וזה מקצר את הדרך משמעותית:

| רכיב קיים | תפקידו כאן |
|---|---|
| `POST /api/claude-session/proposal` (‎`x-cron-secret`‎) | **תבנית הקליטה** — אותו דפוס M2M |
| `task_session_reports` | הוכחה שיומן-סשנים פר-סשן עובד |
| `claude_daily_identity`, `claude_known_workers` | המערכת **כבר** מודלת כמה חשבונות Claude |
| `experiment_runs` (+ QC) | דפוס הרצות ותוצרים |
| ‎`build-session-proposal.mjs`‎ | כבר קורא `hook.transcript_path` — **התמלול המלא בהישג יד** |

## 4. הפרוסה הראשונה — מה נבנה

**"לחיצה אחת באפליקציה מריצה את Claude, וכל מה שקרה נשמר אצלנו."**

| שכבה | מה |
|---|---|
| **DB** | `claude_runs` (הרצה) + `claude_run_events` (כל אירוע — הזרם המלא) |
| **API** | `POST /api/claude/runs` (הפעלה) · `GET /api/claude/runs` (רשימה) · `GET /api/claude/runs/:id` (הרצה + כל האירועים) |
| **מנוע** | `runner.ts` — מריץ את המנוע, מנתח את זרם ה-NDJSON, כותב כל אירוע ל-DB |
| **מסך** | `/claude` — הפעלה, רשימת הרצות, וצפייה בזרם המלא |

**הערת יישום — למה CLI ולא ה-SDK בשלב הזה.** ה-SDK **עוטף** את אותו מנוע ואת
אותו זרם אירועים, ולכן ההחלטה היא בעיקר על צורת ההרצה. בשלב 1 אנחנו מריצים את
התהליך ישירות עם `--output-format stream-json`. מעבר ל-SDK בהמשך הוא drop-in —
**צורת האירועים זהה**, וזה מה שמאפשר להחליף בלי לגעת בסכימה או במסך.

> **תיקון להנמקה המקורית.** כתבתי כאן שהיתרון הוא "אפס תלות חדשה". **זה לא
> נכון:** מכונת ה-Railway מריצה `nixPkgs = [nodejs_22, ffmpeg]` בלבד, בלי
> `claude` — כך שההרצה היתה נכשלת ב-`spawn claude ENOENT`. לכן
> `@anthropic-ai/claude-code` **נוסף כתלות של ה-backend**, וכיוון שההרצה היא
> `node dist/index.js` (לא סקריפט npm) ו-`node_modules/.bin` אינו ב-PATH,
> הרנר **פותר את נתיב הבינארי במפורש**. המשמעות: התלות נוספת בכל מקרה, ולכן
> ההנמקה האמיתית לבחירת ה-CLI היא **קוד מאומת ופחות שינוי**, לא חיסכון בתלות.

**אימות (`CLAUDE_CODE_OAUTH_TOKEN`).** טוקן מ-`claude setup-token` על המנוי.
⚠️ **חשוב:** `ANTHROPIC_API_KEY` **גובר** על המנוי — אם הוא מוגדר בסביבה,
ההרצה תיפול לחיוב-API. הרנר **מנקה אותו במפורש** מסביבת התהליך.

⚠️ **אישור-עלות (CLAUDE.md) נשמר.** עבודת Claude על המנוי אינה טוקני-API. אבל
הרצה שמפעילה **fal בתשלום** (יצירת/תיקון תמונות) חייבת אישור-עלות מפורש לפני
ההרצה — הכפתור **לא** עוקף את השער.

## 5. שאלת החשבונות — פרט יישום, לא לב העניין

בבדיקה הראשונה הצגתי את מיפוי החשבונות כלב התוכנית. **זו היתה זווית שגויה** —
זה פרט יישום שנפתר כשצריך. מה שכן שווה לדעת:

- התוכנית הנעולה [`user-routing-stop-hook-plan.md`](../user-routing-stop-hook-plan.md)
  מניחה **חשבון מנהל אחד** (קבוע בקוד) ו**חשבונות משותפים לעובדים**. שתי
  ההנחות השתנו: כמה חשבונות למנהל (אחד לפרויקט), ולכל עובד מושב משלו ב-Team.
- לכן, **כשנגיע לשלב 4**, המיפוי הקשיח יהפוך לטבלה מנוהלת (`claude_accounts`)
  עם הטוקן המוצפן לכל חשבון. **לא נוגעים בזה עד אז.**
- בשלב 1 החשבון נשמר על ההרצה כשדה טקסט (`claude_account`) — מספיק, ומשאיר את
  הדרך פתוחה.

## 6. מגבלות אמיתיות (מ-`feasibility.md`)

- **אין פיד-יתרה תוכניתי ב-Team.** ה-Analytics API הוא **Enterprise בלבד**; ב-Team
  יש [דשבורד](https://claude.ai/analytics/claude-code) + ייצוא CSV. נציג
  **צריכה**, לא "יתרה מהשרת".
- **אין אות-מכונה ל"נעצרתי מחמת מגבלה"** — רק טקסט-שגיאה + watchdog מקדים.
- **סשן של עובד — צפייה בלבד.** טוקן `setup-token` מריץ מודל בלבד (בלי Remote
  Control), ולכן אי אפשר להזריק פקודה לסשן אינטראקטיבי חי של עובד. הרצה
  שהאפליקציה פתחה — שליטה מלאה.

## 7. פתוחים

1. **איפה רץ הרנר** — ה-backend ב-Railway צריך את ה-CLI מותקן (`nixpacks.toml`).
   בשלב 1 הקוד עובד בכל מקום שיש בו `claude` ב-PATH.
2. **תור אמיתי** — בשלב 1 ההרצה מתחילה בתהליך של הבקשה (fire-and-forget). לעומס
   אמיתי צריך worker.
3. **הצפנת טוקנים** — רלוונטי משלב 4.

## 8. מה במפורש **לא** נבנה

- סיבוב חשבונות לעקיפת מגבלות (החלטת המשתמש: חשבונות למטרות נפרדות).
- אמידת-מכסה מדויקת (אין ממה לגזור ב-Team).
- חשיפת החשבונות/הקיבולת ללקוחות-קצה.
