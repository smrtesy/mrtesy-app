# קונסולת הקלוד — שימור הקשר וחוויית סשן-חי

> מסמך החלטה. נכתב לאישור לפני קוד. שתי שכבות בלתי-תלויות: **(א)** שחזור-הקשר
> מה-DB — סוגר את הבאג של "התור פתאום שכח הכל"; **(ב)** שדרוג "עצור/תור" —
> מקרב את החוויה לדפדפן. השכבות עצמאיות; אפשר לממש (א) לבד.

## הבעיה (השורש, לא הסימפטום)

הקלוד המובנה מאבד את רצף השיחה באמצע — הבאנר "התור הזה התחיל סשן חדש — הוא
לא מכיר את מה שנאמר לפניו" (`contextLost`, `ClaudeChat.tsx:1481`). הסיבה:

1. כל שרשור = שיחה אחת. כל תור מריץ `claude -p … --resume <session_id>`
   (`runner.ts:716`), והמנוע חסר-מצב — הוא מזין מחדש את **כל** תמליל השיחה בכל
   תור. התמליל יושב כקובץ מקומי תחת `~/.claude/projects/<cwd-מקודד>/<id>.jsonl`.
2. ה-backend רץ ב-Railway בקונטיינר **חד-פעמי** שמתאתחל בכל דיפלוי ל-`main`,
   קריסה, או הגירת-מארח. אתחול → הדיסק המקומי נמחק → התמליל נעלם.
3. התור הבא: `--resume` לא מוצא תמליל, נופל עם *"No conversation found"*, והקוד
   (`runner.ts:967-980`) מתאושש כ**סשן חדש נקי** — `resumed_session=null`. זה
   הבאנר.

**הראיה שההיסטוריה עצמה לא אבודה:** כל אירוע נשמר ב-`claude_run_events` שלנו —
DB דורבילי. מה שנשמר על הדיסק החד-פעמי הוא רק הזיכרון של המנוע, לא מקור-האמת.

**התובנה המכריעה:** claude.ai בדפדפן עושה בדיוק את זה — המודל חסר-מצב, השיחה
נשמרת ב-DB, ובכל תור נטענת ונשלחת מחדש. אנחנו **כבר** מזינים הכל מחדש כל תור;
הפער היחיד הוא שאנחנו קוראים את "הכל" מדיסק חד-פעמי במקום מ-DB דורבילי.

## למה שחזור-מ-DB ולא דיסק-קבוע / שירות-נפרד / פלטפורמה אחרת

נבחנו (מסמך נפרד בדיון): Railway Volume (נועל את כל ה-backend לרפליקה יחידה +
downtime בכל דיפלוי), שירות-נפרד (מנתק מדיפלויי-האפליקציה אבל הדיסק עדיין
חד-פעמי, ו-idle יכול להחמיר), ו-Fly/Cloudflare (מתאימים יותר לסשן-חי אך הגירה
גדולה, **ועדיין** דורשים החצנת-מצב מתחת). המכנה המשותף: **כל ארכיטקטורה דורשת
את שכבת ההקשר-הדורבילי ממילא.** לכן זו השכבה הראשונה, והזולה — שינוי ממוקד בקוד,
בלי נגיעה בתשתית, על המנוי (אפס טוקני API בתשלום), ורק בנתיב-ההתאוששות.

## שכבה א — שחזור-הקשר מה-DB

**היכן:** `server/src/modules/claude/runner.ts`, ענף ההתאוששות
(`if (initialResume && resumeMissing)`, ~שורה 974) — היום מריץ `runEngine(null)`
עם הפרומפט של המשתמש בלבד ובלי הקשר.

**השינוי:** לפני הרצת הסשן החדש, לבנות מחדש את תמליל השיחה מ-`claude_run_events`
ולהזריק אותו כרקע. **מנגנון ה-seed כבר קיים** (method-B לשרשורי-פיצול,
`runner.ts:676`) — נשתמש בו מחדש. `buildArgs` קורא את `promptText` בזמן-קריאה,
אז מספיק להשַׁמות אותו מחדש לפני `runEngine(null)`.

**בניית התמליל:**
- שליפה: כל ה-`claude_runs` של ה-`thread_id` לפי `created_at`, ולכל אחד
  אירועי `claude_run_events` לפי `seq`.
- פורמט: תורי `user`/`assistant` (טקסט), + סיכום קומפקטי של `tool_use`/
  `tool_result` (שם הכלי + תמצית) כדי לשמר "מה נעשה".
- **חשוב:** התמליל נבנה **רק מאירועים שלמים שנשמרו** — לא מקובץ שהריגה עלולה
  להשאיר באמצע-כתיבה. לכן השחזור חסין-עקביות יותר מ-`--resume` טבעי.

**תקציב (מגבלת argv 100KB, `runner.ts` / `playbooks.ts`):**
- מתחת לתקציב → הזרקה inline כ-seed.
- מעל → כתיבת `conversation-history.md` ל-`cwd` והנחיה למנוע לקרוא אותה (עוקף
  את מגבלת ה-argv; מתאים לשיחות ארוכות). חלופה: סיכום החלק הישן + התורים
  האחרונים כלשונם (הסיכום על המנוי, אפס טוקנים בתשלום).

**באנר:** כשהשחזור הצליח, `contextLost` הופך למטעה. להחליף לנוסח רך —
`contextRestored`: "השיחה שוחזרה מההיסטוריה" (מפתח חדש ב-`he.json`+`en.json`,
באותו קומיט). את הנוסח הישן לשמור כ-fallback רק אם השחזור באמת יצא ריק.

**מה לא משתנה:** זרימה רגילה. `--resume` טבעי ממשיך לעבוד; ההזרקה קורית **רק**
בכשל-resume. בפועל — אירוע נדיר, פעם לכל אתחול, לא כל הודעה.

**כנות:** ההקשר המשוחזר הוא replay נאמן (רקע), לא היסטוריית-סשן טבעית של המנוע.
לצ'אט — כמעט זהה; לעבודת-כלים/קבצים כבדה — קצת פחות נאמן. פותר את הכאב במלואו.

**היקף:** `runner.ts` (+ helper קטן לבניית התמליל), 2 מפתחות i18n, נוסח הבאנר
ב-`ClaudeChat.tsx`. בלי מיגרציה, בלי תשתית.

## שכבה ב — "עצור / תור" (החוויה של הדפדפן)

**מה claude.ai באמת עושה כש"שולחים באמצע":** לא מזריק לתוך ג'נרציה רצה (בלתי-
אפשרי — יצירה אוטו-רגרסיבית). הוא **עוצר, שומר את הפלט החלקי כתור, וההודעה
הבאה היא תור חדש** עם כל ההיסטוריה מחדש. את זה אנחנו יכולים לתת עם רכיבים
קיימים:
- **עצור** → `cancelRun` קיים (`runner.ts:235`, SIGTERM→SIGKILL).
- **שליחה תוך-כדי** → תור קיים (סטטוס `waiting`, `ClaudeChat.tsx`).
- **פלט חלקי נשמר** → אירועים נכתבים תוך כדי זרימה ל-`claude_run_events`.

**מה להוסיף:** כפתור "עצור" גלוי בזמן ריצה, ולתת להודעה החדשה לרוץ מיד כתור הבא.

**בטיחות עצירה — למה זה בסדר:**
- **שרשורי צ'אט (בלי ריפו):** נקי כמו claude.ai — רק טקסט, אין תופעות-לוואי.
  עצירה משאירה תשובה חלקית תקינה. **בטוח להציע היום.**
- **שרשורי ריפו-סוכן:** הריגה קשה יכולה להשאיר עץ-עבודה מלוכלך — אבל **מוכל**:
  תיקיית עבודה חד-פעמית לכל-שרשור, git הפיך (`merge --abort` / `checkout`),
  וכלום לא מגיע ל-`main` בלי שתור השלים pre-push. מלוכלך-אך-הפיך, לא נזק
  לפרודקשן.

**עצירה-רכה אמיתית לעבודת-סוכן** (עצירה בגבולות-כלי, בלי kill) דורשת
`interrupt()` של ה-Agent SDK ב-streaming mode — ה-build הגדול (ראה למטה).

## מה דורש את מעבר ה-Agent SDK (לא עכשיו)

| יכולת | היום (CLI `-p`) | דורש Agent SDK streaming |
|---|---|---|
| שחזור-הקשר בכשל | ✅ שכבה א | — |
| עצור + תור טבעי | ✅ שכבה ב | — |
| סשן חי מתמשך (תהליך אחד) | ❌ spawn-לכל-תור | ✅ |
| עצירה-רכה בגבולות-כלי | ❌ רק kill מוכל | ✅ `interrupt()` |
| כיוון forward-pass באמצע | ❌ בלתי-אפשרי | ❌ (גם claude.ai לא) |

ה-SDK swap "drop-in" מתייחס לזהות **זרם-האירועים** (ה-DB וה-UI לא משתנים
בפרסינג) — לא למחזור-החיים. סשן-חי הוא קוד lifecycle חדש (ניהול תהליכים,
stickiness לאינסטנס, transport זורם), ו**עדיין נשען על שכבה א מתחתיו**.

## סדר מימוש מוצע

1. **שכבה א** — שחזור-DB. פותר את הכאב מיד, שינוי ממוקד, בלי תשתית.
2. **שכבה ב** — "עצור/תור", תחילה לשרשורי-צ'אט (בטוח), אחר-כך לריפו.
3. **בעתיד, רק אם הקונסולה נעשית מרכזית** — הערכת מעבר Agent SDK / פלטפורמה
   (Fly/CF) לסשן-חי אמיתי.

## עלות

הכל על המנוי — אפס טוקני API בתשלום. שכבה א רצה רק בהתאוששות (נדיר). אין עלות
תשתית חדשה. עלות ההגדלה היחידה היא הנדסית, ומדורגת לפי הסדר לעיל.
