## הבעיה (השורש)

הקלוד המובנה מאבד רצף באמצע — הבאנר `contextLost` (`ClaudeChat.tsx:1481`).
הסיבה: כל תור מריץ `claude -p … --resume` (`runner.ts:716`); המנוע חסר-מצב
ומזין מחדש את כל התמליל בכל תור; התמליל יושב על **הדיסק החד-פעמי** של Railway
(`~/.claude/projects/…`) ונמחק בכל אתחול קונטיינר (דיפלוי/קריסה/הגירה). ההיסטוריה
עצמה **לא** אבודה — היא ב-`claude_run_events` (DB דורבילי). זו בדיוק השיטה של
claude.ai: stateless + הזנה-מחדש מ-DB. הפער היחיד — אנחנו קוראים מדיסק חד-פעמי
במקום מ-DB.

## 1. שחזור-הקשר מה-DB (השכבה הבסיסית)

**היכן:** `runner.ts`, ענף ההתאוששות (`if (initialResume && resumeMissing)`,
~974) — היום מריץ `runEngine(null)` בלי הקשר. **השינוי:** לפני הרצת הסשן החדש,
לבנות מחדש את התמליל מ-`claude_run_events` ולהזריק כרקע (מנגנון ה-seed של
method-B כבר קיים, `runner.ts:676`; `buildArgs` קורא `promptText` בזמן-קריאה).
**תקציב argv 100KB:** מתחת → inline; מעל → כתיבת `conversation-history.md`
ל-cwd + הנחיה לקרוא, או סיכום-ישן + אחרון-מילה-במילה (compaction). **באנר:**
`contextLost` → `contextRestored` רך (מפתח חדש ב-`he/en.json`). **לא משתנה:**
זרימה רגילה; ההזרקה רק בכשל-resume (נדיר).

## 2. חוויית סשן-חי / "עצור-תור"

**מה claude.ai באמת עושה ב"שליחה באמצע":** לא מזריק לג'נרציה רצה (בלתי-אפשרי) —
**עוצר, שומר פלט חלקי כתור, וההודעה הבאה = תור חדש** עם היסטוריה מלאה. אצלנו
הרכיבים קיימים: `cancelRun` (`runner.ts:235`), תור (`waiting`), ואירועים
נשמרים תוך כדי זרימה. **להוסיף:** כפתור "עצור" גלוי + הרצת ההודעה החדשה כתור הבא.
**סשן מתמשך אמיתי** (תהליך אחד, cache חם, עצירה-רכה) דורש מעבר ל-Agent SDK
streaming — build גדול, **ועדיין נשען על שחזור-DB מתחתיו**.

## 3. ניהול-מודלים

קלוד קוד **לא** מנתב אוטומטית משימות קלות למודל מהיר — המודל שנבחר מריץ הכל.
(המנגנונים הקיימים — `opusplan`, Advisor, `fallbackModel`, מודל-לסוכן-משנה —
כולם מפורשים ויזומים, לא נתב-לפי-קושי.) ניתוב הוא הכרעה שיכולה להוריד איכות
בשקט — לכן מעצבים אותו כמו כלל "מודל מציע, קוד מאשר":

- **נתב-חוקים דטרמיניסטי** (על עובדות-בקוד: יש ריפו? משימת-רקע? צריך כלים?) —
  הכי בטוח, כי אלה עובדות ולא ניחוש.
- **נתב מבוסס-מודל** — רק למקרה עמום, **מוטה-להסלמה** (בספק → מודל חזק).
- **מודל-רקע לפי סוג-משימה — לא "רקע→מהיר" גורף:**
  - **טריוויאלי-מכני** (יצירת כותרת, שורת-סיכום) → מודל **מהיר** (Haiku). בטוח.
  - **ניתוח/החלטה** (הצעות פיצול/קיבוץ, ניתוחי-שרשור) → מודל **חזק** (מוגדר,
    ברירת-מחדל חזקה). **לעולם לא להוריד מודל במשימת-החלטה** — זה בדיוק אזור-הסכנה
    של "מודל מציע, קוד מאשר" (המיזוגים השגויים). בקוד: רק הכותרת
    (`threads.ts:1040`) טריוויאלית; הצעת-הפיצול (`threads.ts:1372`) והניתוחים
    (`analysis.ts`) הם שיפוט → נשארים חזקים.
- **תיעוד + דיטקטור** על תורים שתת-שורתו (קיבלו "תעשה מחדש") — כמו
  `check_cross_party_merges`.

**חיווי-מודל (דרישה, לא רק נחמד):** כל בחירת-מודל חייבת להיות **גלויה ומתועדת**,
כדי לראות איזה מודל יצר איזו תוצאה (תואם "הכל גלוי" ב-video-lab). שני חלקים:
- **תורים ראשיים:** הנתון כבר קיים (`claude_runs.model` + `modelUsage`) — רק
  להציג תווית-מודל פר-תור ב-UI.
- **משימות-רקע:** פער — `runOneShot` לא יוצר שורת-ריצה, אז המודל לא נרשם בשום
  מקום. אם מנתבים משימות-רקע למודלים שונים, **חובה להתחיל לרשום את המודל** (על
  רשומת הניתוח / לוג), אחרת הניתוב בלתי-נראה ואי-אפשר להעריך מודל→איכות.

**התחל מ:** חוקים דטרמיניסטיים + כותרות→מהיר (ניתוחים נשארים חזקים) + חיווי-מודל.
נתב-מודל מלא = build שלא מצדיק עצמו עד שהשימוש כבד.

## 4. מהירות תגובה (בלי לגעת במודל)

- **מהירות נתפסת (הזכייה הגדולה-הזולה):** ✅ **מומש** — ה-flush הודק מ-25/1000ms
  ל-`FLUSH_EVERY=8`/`FLUSH_INTERVAL_MS=500` וה-UI ב-`POLL_MS=900`, כך שהפלט
  מגיע ל-DB ול-UI בערך פי-2 מהר. הידוק עיוור נוסף רק יעמיס על Supabase בלי
  תועלת — הצעד הבא כאן הוא **SSE/WebSocket** (#13), לא כוונון נוסף.
- **`effort` לפי סוג-משימה** — הידית הכי חזקה שאינה מודל. **לא גורף.**
- **צמצום הקשר (prefill)** — הידוק ההוראות-הקבועות/playbook. **בזהירות** —
  לא לחתוך הנחיות נושאות-משקל.
- **צמצום תקורת-הכנה** — `mintAppAccess`/דפדפן/`trustWorkspace` רצים לפני המודל
  בכל תור (`runner.ts:648-705`); להפוך app-access ל-**opt-in**.
- **שמירת cache חם + חלון-מנוי** — סשן מתמשך (SDK) שומר cache חם; ניתוב עבודת-רקע
  לחשבון `AUTOMATION_ACCOUNT` (כבר קיים) שומר את החלון האינטראקטיבי פנוי.

## סדר מימוש מומלץ

1. **שחזור-DB (1)** — סוגר את הכאב, שינוי ממוקד, בלי תשתית.
2. **זכיות מהירות זולות (12, 16)** + **Haiku-לרקע (10)** + **נתב-חוקים (7)**.

   למקרה הנפוץ; ה-UI זהה לשני המשטחים, אז בונים ומאמתים אותו על המשטח הבטוח
   קודם. **הפרדה:** ה"תור" (שליחה-תוך-כדי) בטוח בכל מקום; רק ה"עצירה-שהורגת"
   מדורגת — בריפו היא יכולה לקטוע כלי/git, אז דורשת ניקוי-אחרי (הרדיוס מוכל)
   או עצירה-רכה דרך ה-SDK.
4. **בעתיד, לפי הצדקת-שימוש:** SSE (13) → סשן מתמשך SDK (5) → הערכת פלטפורמה (4).
