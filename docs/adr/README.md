# החלטות-ארכיטקטורה מתועדות (ADR)

הערוץ שבו איימן (או כל מפתח) מציע **שיטה טובה יותר** — כתוב, מתועד, אך
**לא חוסם** את העבודה השוטפת עד שחנוך מאשר. ADR = מסמך קצר (10–20 דקות
כתיבה) שמתעד החלטה טכנית אחת, ההקשר שלה והמחיר שלה. פרטים על מקומו בזרימה:
`docs/dev-workflow.md` §8.

## איך זה עובד

1. יש לך רעיון לשנות קונבנציה / להחליף גישה? פתח קובץ חדש כאן:
   `docs/adr/NNNN-<slug>.md` (מספר רץ, למשל `0001-use-sse-not-websockets.md`).
2. מלא את התבנית למטה. **המצב ההתחלתי תמיד `Assess`** (מדרג האימוץ:
   Hold / **Assess** / Trial / Adopt).
3. כדי לעלות מ-`Assess` ל-`Trial` — השיטה חייבת להוכיח עצמה על **מקרה-אמת
   אחד** (*בדיקת השוואה*: החדשה מול הקיימת, אותה משימה, שתיהן עוברות את
   פרוטוקול לפני-הדחיפה). ניצחה בראיה? חנוך מקדם ל-`Adopt` והיא נכנסת
   לדרך-הסלולה. לא? נשארת מתועדת — לא שכתבנו קונבנציה על סמך הרגל בלבד.

## תבנית — העתק לקובץ חדש

```markdown
# NNNN — <כותרת ההחלטה>

- מצב: Assess            # Assess → Trial → Adopt (או Hold)
- תאריך: YYYY-MM-DD
- מציע: <שם>

## ההקשר / הבעיה
מה לא טוב בשיטה הנוכחית? מה מנסים לפתור?

## ההצעה
מה אני מציע במקום, בקצרה.

## אלטרנטיבות שנשקלו
2–3 גישות + היתרון/החיסרון של כל אחת (כולל להישאר עם הקיים).

## המחיר / ההשלכות
מה זה עולה (זמן, סיכון, מה נשבר, מה צריך ללמוד מחדש).

## הראיה (למעבר ל-Trial)
תוצאת בדיקת-ההשוואה על מקרה-אמת אחד — מספרים, לא דעה.
```
