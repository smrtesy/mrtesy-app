## 0. מי זה ומה המטרה

**איימן** — מפתח בכיר בשכר-שעתי, **קבלן חיצוני** (מייל `dev@maor.org`,
כבר הוסר ממנהלי-העל). המטרה: להביא אותו למצב שבו הוא יכול לבצע עבודת
פיתוח על `mrtesy-app` — בלי לאבד את הכיוון של חנוך, בלי לשרוף שעות,
ובלי גישה לסודות המערכת או למידע האישי של חנוך.

**חלוקת התפקידים** (מפורט ב-`dev-workflow.md`): חנוך = אסטרטג (ה"מה"
וה"למה"); איימן = מבצע-חושב (ה"איך"); מנוע *קלוד* = מכפיל-כוח + עדשה
שמתרגמת לחנוך מה נבנה בלי שיקרא קוד.

## 3. החלטות פתוחות שחוסמות את החבילה

1. **בטא/יציב** — אותו-deploy מגודר מול סביבה-נפרדת. זו הסיבה שמסמכי
   הענף לא מוזגו קודם. חנוך אומר שהתוכנית סגורה → צריך להעלות/לכתוב את
   המסמך ולסגור את התלות.
2. **סקופ המשימה הראשונה של איימן** — frontend / backend / repo נפרד.
   קובע את בחירת סביבת-הבידוד: אפשרות A (מקומי + DB שני ריק) מול D
   (frontend-בלבד מול backend של חנוך).
3. **נתונים חיים לבדיקות** — seed סינתטי / snapshot מנוקה / mocks /
   העתקת מידע-לא-אישי. מי בונה את ה-seeder.

## 4. המשימה הראשונה של איימן (פריט 10)

מוצעות שתיים, בסדר עולה:
1. **חימום:** לכתוב את `docs/dev-handbook.md` — בטוח, לא יכול לשבור
   כלום, מכריח קריאת-חוקה, מריץ פרוטוקול לפני-דחיפה פעם אחת מקצה-לקצה.
2. **פיילוט אמיתי** (`aymen-onboarding-plan.md` §8 + env-handoff §5):
   לסגור את פער ה-`is_private` ב-API — ליצור **דרגת-גישה אמצעית**
   (אפליקציה מלאה בלי המשימות הפרטיות של הבעלים). מוכל, קריטי-לבטיחות,
   מלמד את הקוד, ומשמש **מבחן-חי לכל השיטה**.
