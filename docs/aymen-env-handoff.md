## 1. ההקשר / הבעיה

חנוך מגייס את **איימן** (מפתח שעתי) לעבוד על smrtesy (`mrtesy-app`). הדרישות:

- **לאיימן:** גישה לכל הפיצ'רים כדי לפתח. **לא** גישה למידע האישי של חנוך,
  ו**לא** להחזיק את הסודות/מפתחות של השירותים.
- **עובדי מאור** יעבדו על המערכת. חנוך בסדר שהם רואים **מידע ארגוני**, אבל
  **לא מידע אישי** שלו. בנוסף הוא רוצה לבנות **מעקב-עובדים** — ולכן הוא כן
  צריך גישה לכל המידע *שלהם*.
- **שאלת-על עתידית:** מודל **בטא/יציב** — חנוך רץ על בטא מלא, העובדים על
  משטח מגודר של פיצ'רים שנבדקו.

## 2. עקרונות שהוכרעו בדיון (הכיוון)

- **גבול-DB = סביבות, לא אנשים.** מפרידים את איימן ב**סביבה** (DB פיתוח);
  מפרידים את חנוך מהעובדים ב**org + תפקיד + `is_private`** — על אותו DB.
  חברות משתמשות בגבול-DB רק לשני דברים: הפרדת-סביבות (פרודקשן/פיתוח) וקנה-מידה
  עצום (sharding). בין אנשים — תמיד DB אחד + תפקידים + שורות.
- **לא מפצלים DB לשיתוף מידע חי.** שני DB שצריכים להראות אותו מידע = רפליקציה
  + פתרון-קונפליקטים, והאינטגרציות מזינות DB אחד בלבד. כאב מיותר.
- **עקרון-הסוד המכריע:** *סוד מוסתר מהמפתח רק אם הקוד שמשתמש בו רץ במקום שאין
  לו בו shell* (השרת שלך / ה-CI שלך). כל סוד שמוזרק לסביבה שיש למפתח בה
  טרמינל — הוא קוראו ב-`printenv`. ⇒ Codespaces = נוחות, **לא** הסתרת-סוד;
  "המפתח מריץ רק frontend מול backend שלך" (אפשרות D) כן מסתיר.
- **שלוש הרשאות נפרדות:** `repo access ≠ secret access ≠ prod-DB access`.
  הסודות לא יושבים בגיט אלא ב-Railway/Supabase env, לכן אפשר לתת קוד בלי סודות.
- **עובד צריך "מסך נקי", לא "DB נקי".** גידור פיצ'רים על אותו DB. DB ריק =
  בשביל המפתח בלבד.
- **תפקיד ≠ הגנת-מידע.** תפקיד/הרשאה מגן על *משתמש בזמן-ריצה*; מפתח שמריץ את
  הקוד ומחזיק את ה-service-key עוקף אותו. לכן: **תפקיד = מיקוד (על מה עובד),
  DB נפרד = הגנה (על המידע).**
- **למידע רגיש: seed סינתטי מנצח snapshot-מנוקה** — ניקוי טקסט-חופשי שביר,
  וכישלון-ניקוי שקט = הדלפה לתוך DB שהמפתח מחזיק את המפתח שלו.

## 4. האפשרויות שנשקלו — A עד D + טכניקות משלימות

### A — מקומי + project Supabase שני (schema clone ריק)
איימן מריץ frontend+backend **מקומית**, מכוון ל-**project Supabase חדש**
(service-key נפרד → פיזית לא מגיע למידע של חנוך). מתחבר עם ה-dev-login הקיים
כמשתמש מזויף. אינטגרציות בתשלום כבויות/מפתחות-זבל לפי הצורך. ה-DB עצמו =
שכפול-סכימה ריק (`pg_dump --schema-only`).
- **טוב:** בידוד אמיתי; משתמש בבניין-אב שכבר קיים (dev-login); אפס
  סיכון-פרודקשן; זול ומהיר.
- **פחות טוב:** צריך להקים project שני + לכתוב seeder; פיצ'רים מונעי-אינטגרציה
  לא "רצים" בלי חשבון-זבל; לאצור תת-קבוצה מ-~96 ה-env.
- **סטטוס:** ההמלצה ליום 1.

### B — Supabase מקומי (CLI/Docker) או preview-branches
DB חד-פעמי שמתאפס — `supabase start` (Postgres+Auth+Storage מקומי) או
ענפי-preview.
- **טוב:** ייעודי בדיוק לזה, מתאפס, אפס עלות-ענן (מקומי).
- **פחות טוב:** 250+ מיגרציות חייבות לרוץ נקי מקומית — וה-`CLAUDE.md` מזהיר
  שהיסטוריית-המיגרציות מנוהלת בנפרד (לא `db push`), אז replay נקי לא מובטח;
  צריך Docker; branching = פיצ'ר חדש/בתשלום (לאמת מחיר).

### C — סביבה מקבילה מלאה בענן (staging)
Vercel + Railway + Supabase staging, עם חשבונות-בדיקה חיצוניים.
- **טוב:** נאמנות גבוהה; אינטגרציות ל-sandbox; **וזו בדיוק תשתית בטא/יציב** —
  עבודה שמשרתת פעמיים.
- **פחות טוב:** הכי כבד — ~96 env × שתי פלטפורמות + סודות כפולים + pipeline
  שני + עלות שוטפת. Overkill רק כדי לגייס מפתח אחד.
- **סטטוס:** לבנות כשמכריעים בטא/יציב, לא רק לאונבורדינג.

### D — המפתח לא מחזיק שום סוד (frontend-בלבד מול backend שלך)
**חנוך** מריץ backend-staging אחד שהוא שולט בו, והסודות יושבים רק בו. איימן
מריץ **רק frontend** מקומית (או container מתוחם), מכוון ל-backend של חנוך,
נכנס עם dev-login ל-org סינתטי. הוא **לא מחזיק** service-key, מפתח Anthropic,
או אף סוד. org-scoping + אין service-key = פיזית לא יכול להגיע לדאטה — גם אם
זה אותו DB (המפתח בידי חנוך, לא בידו; איימן חוזר להיות "משתמש-ריצה").
- **טוב:** המפתח לא מחזיק כלום; הכי חזק ל**מפתח חדש/קבלן שעוד לא בנית איתו
  אמון**. זה הפוך מ"תפקיד לא מגן" — כי כאן איימן לא מריץ backend.
- **פחות טוב:** **frontend-בלבד ישים.** מפתח שמריץ רק frontend **לא יכול
  לפתח backend** (רוב העבודה כאן ב-`server/`). שינוי-backend דורש מחזור-deploy
  מול ה-backend של חנוך = לולאת-פיתוח איטית. מתאים רק אם סקופ איימן = frontend/UI.

### טכניקות משלימות (הזינו את שאלת "נתונים חיים לבדיקות")
- **CDE / GitHub Codespaces / Gitpod:** סביבת-פיתוח בענן. **טוב לנוחות**
  (הקמה בקליק, devcontainer משוחזר) — **לא גבול-אבטחה**: למפתח יש טרמינל
  ב-codespace, `printenv` חושף כל סוד מוזרק. כלי-נוחות, לא הסתרת-סוד.
- **Data anonymization / snapshot מנוקה:** snapshot פרודקשן → `faker` מחליף
  שמות/מיילים/טקסט רגיש → נטען ל-DB פיתוח. **סיכון:** ניקוי **טקסט-חופשי**
  (תיאורי משימות, גוף הודעות) שביר; הכל שייך לחנוך היום, אז ניקוי גרוע =
  הדלפה. סותר את עקרון "סינתטי מנצח מנוקה" למידע רגיש.
- **API mocking / record-replay:** מיירטים בקשות ל-Gmail/Drive/וואטסאפ/
  Anthropic ומחזירים תשובה קבועה. טוב ל-UI ובלי חשבון חי. הערה: MSW הוא
  בעיקר כלי frontend/טסטים; לאינטגרציות ב-`server/` צריך fake/cassette
  צד-שרת.

## 5. ההמלצה שיוצאת (ביניים)

- **איימן ⇒ אפשרות A** ליום 1: מקומי + DB שני = שכפול-סכימה ריק. ריק = בטוח
  לחלוטין (כל המידע של חנוך). בלי סודות-פרודקשן; dev-login הקיים.
- אם סקופ איימן = **repo נפרד** (video-lab/voice-engine) או **frontend-בלבד**
  — הבעיה מתאיידת/מצטמצמת (אפשרות D).
- **עובדים ⇒ אותו DB + גידור**, בדרגת-גישה שמכבדת `is_private`.
- **משימה ראשונה מוצעת לאיימן:** לסגור את פער ה-`is_private` ב-API — ליצור
  את ה**דרגה האמצעית** (אפליקציה מלאה בלי המשימות הפרטיות של הבעלים). מוכל
  (~יום), קריטי-לבטיחות, מלמד את הקוד. מנוסח כ"בעיה + למה" לפי `dev-workflow.md`:
  *"עובד חייב את האפליקציה המלאה אבל לעולם לא לראות משימה פרטית של הבעלים —
  תמצא את הדרך."*
- **בטא/יציב:** להכריע אחרי שהסביבה קמה (הסביבה מכריעה חלק מזה). מסמכי הענף
  עדיין לא ממוזגים ל-main **בכוונה** — חסרה בהם החלטת בטא/יציב.

## 6. מה עוד נשאר לברר

1. **★ השאלה הפתוחה שחנוך רוצה לדון בה עכשיו: איך מספקים לאיימן נתונים חיים
   לבדיקות בקלות?** הקושי: ה-DB הריק חסר נתונים, וכמעט **אין** מידע ארגוני
   לא-אישי (עובדים עוד לא ייצרו). אפשרויות, כל אחת עם catch:
   - (א) **seed סינתטי** — בטוח, אבל צריך לבנות seeder.
   - (ב) **snapshot פרודקשן מנוקה (faker)** — מסוכן (טקסט-חופשי; הכל של חנוך).
   - (ג) **record-replay / mocks** לאינטגרציות — טוב ל-UI, צריך fixtures.
   - (ד) **העתקת מידע לא-אישי בלבד** (`is_private=false` + per-user שאינו
     חנוך) — כרגע כמעט ריק.
   ⇒ להכריע איזו, ומי בונה את ה-seeder.
2. **סקופ המשימה הראשונה של איימן** (frontend / backend / repo נפרד) — קובע
   A מול D.
3. **החלטת בטא/יציב** — אותו-deploy-מגודר מול סביבה-נפרדת.
4. **אודיט:** שכל נתיבי-קריאת-המשימות מכבדים `is_private` — לא רק השליפה
   הראשית (`daily-report`, `events`, `parts`, ספירות).
5. **ברירת-המחדל `full`** חושפת עובד עתידי — לשקול להפוך את הברירת-מחדל, או
   לאכוף דרגה-אמצעית/lite בעת ההקצאה.
