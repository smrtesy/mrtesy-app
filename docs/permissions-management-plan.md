# ניהול הרשאות — תוכנית (permissions management)

> מסמך-תכנון לעשיית סדר בניהול ההרשאות לאורך כל הפלטפורמה. נכתב לאישור לפני
> בנייה. מקור-האמת של החלטות התכנון עד שהוא מוטמע בקוד. Verified: 2026-08-03.

## 1. המטרה

לעשות **סדר** בהרשאות — מבנה אחד קל לניהול ולתכנון, במקום ההרשאות המפוזרות
של היום (שני ממשקי-ניהול נפרדים, שתי טבלאות עם שמות כמעט-זהים, ואפס הגבלה
ברמת פרט בתוך אפליקציה).

## 2. המודל — שלוש רמות + "פתוח כברירת מחדל בתוך אפליקציה"

| רמה | מה מותר לה | מה היא מגדירה |
|---|---|---|
| **מנהל-על** (super-admin) | הכול, בכל ארגון | מחזיק את **קטלוג בני-ההגבלה** (מוגדר בקוד) + ברירות-מחדל פלטפורמתיות |
| **מנהל-ארגון** (owner / admin) | הכול, בארגון שלו | **מסמן מה מוגבל** בארגון, ו**נותן חריגות** למשתמשים (ובשלב 2 — מאשר בקשות) |
| **משתמש** (member) | האפליקציות שהוקצו לו; בתוך כל אחת — הכול | — |

**עיקרון-העל: הופכים את הכיוון.** היום המודל הוא רשימת-היתר (member מקבל רק מה
שהוקצה). המודל החדש, **בתוך אפליקציה שכבר הוקצתה**: הכול פתוח כברירת-מחדל, וההגבלות
חוֹתכות פרטים ספציפיים בלבד.

**מה שלא משתנה:** הקצאת-האפליקציות עצמה נשארת בדיוק כמו היום — אפליקציות מוקצות
למשתמש אחת-אחת (`user_app_access`). המודל החדש יושב **מעל** זה, לא במקומו.

### 2.1 רמת ההגבלה

הגבלה חלה על אחד משני אלה בלבד (הוכרע):

- **מסך / מסך-משנה** — למשל: בתוך smrtTask, המסך `/knowledge` מוגבל בעוד `/tasks` פתוח.
- **פעולה מסוכנת** — למשל: מחיקה, שליחת מייל, או **הרצה בתשלום** (השלב-2 החשוב).

לא ברמת אפליקציה שלמה (זו כבר ההקצאה), ולא ברמת רשומה/שדה בודד (מורכב מדי כרגע).

### 2.2 smrtTask — בסיסי מול מלא

smrtTask הוא מקרה מיוחד עם שתי דרגות (הוכרע):

- **בסיסי** — אוטומטי ל**כל** חבר-ארגון, בלי הקצאה ובלי אונבורדינג: תיבת-ההתראות
  שלו + המשימות/תקשורת ששייכות לו.
- **מלא** — רק למי ש-smrtTask **הוקצתה** לו: אונבורדינג, חיבור Gmail/Drive/WhatsApp/
  Calendar, סריקה, חילוץ-AI, וכל המסכים.

## 3. חלוקה לשלבים

| רכיב | שלב 1 (בונים עכשיו) | שלב 2 (רק מתאימים מבנה) |
|---|---|---|
| שלוש שכבות ההגדרות (על / ארגון / משתמש) | ✅ | |
| קטלוג בני-ההגבלה (בקוד) + סימון מה מוגבל בארגון | ✅ | |
| אכיפה בשרת (`requireResource`) + מסך-נעול | ✅ | |
| מתן/שלילת חריגה **ידנית** ע"י מנהל-הארגון | ✅ | |
| ממשק-ניהול הרשאות מאוחד | ✅ | |
| יומן-שינויים (audit) | ✅ | |
| ניקוי בלבול שתי הטבלאות + באג ניקוי | ✅ | |
| smrtTask בסיסי-אוטומטי / מלא-מוקצה | ✅ | |
| בקשה-בקליק → התראה → אישור → פתיחה אוטומטית | | ✅ (מבנה בלבד) |
| פעולות-הוצאה: כוון→בקשת-אישור למנהל-פרויקט→ריצה-אוטומטית | | ✅ (מבנה בלבד) |
| מושג "מנהל-פרויקט" כמאשר (נבדל ממנהל-ארגון) | | ✅ (מבנה בלבד) |

**למה זה מתחלק ככה:** לולאת הבקשה-אישור ופעולות-ההוצאה הן החלק העדין (התראות,
תזמון, ריצה-אוטומטית לאחר אישור). שלב 1 בונה את **התשתית** — הגדרת ההגבלות,
אכיפתן, ומתן חריגות ידני — כך שבשלב 2 "אישור בקשה" הוא פשוט כתיבת חריגה, ו"אישור
הוצאה" הוא עוד סוג-בקשה על אותה טבלה. שום דבר בשלב 1 לא צריך להישבר כדי להוסיף את שלב 2.

## 4. מבנה נתונים

### 4.1 קטלוג בני-ההגבלה — מוגדר בקוד

מקור-האמת: `src/lib/permissions/registry.ts` (כמו `lib/apps/registry.ts`).
כל רשומה:

```ts
type RestrictableResource = {
  key: string;                 // יציב, למשל "smrttask.screen.knowledge"
  appSlug: string;             // "smrttask"
  kind: "screen" | "subscreen" | "action";
  labelKey: string;            // מפתח i18n
  descriptionKey?: string;
  defaultRestricted: boolean;  // כרגיל false (פתוח כברירת-מחדל)
  costly?: boolean;            // מסמן פעולת-הוצאה — צרכן שלב 2
};
```

**עדכון-מימוש:** אין טבלת `restrictable_resources` — הקוד הוא מקור-האמת היחיד.
`resource_key` בכל הטבלאות מאומת מול הקטלוג-בקוד בזמן-כתיבה בשרת (`isValidResourceKey`),
כך שאין צורך ב-FK או בסנכרון-טבלה שעלול להיסחף. תוויות נפתרות ב-i18n. לכל משאב יש דגל
`enforced` (חסר = true); משאב לא-נאכף מוצג ב-UI מושבת ("בקרוב") והשרת דוחה הגבלה שלו.

### 4.2 טבלאות שלב 1 (נבנות עכשיו — כולן לא-הרסניות)

**`org_restrictions`** — מה הארגון מגביל:
```
org_id uuid, resource_key text, restricted boolean not null default true,
updated_by uuid, updated_at timestamptz,
primary key (org_id, resource_key)
```
היעדר שורה = ברירת-המחדל מהקטלוג (כרגיל = פתוח).

**`user_resource_grants`** — חריגה למשתמש (מעבר להגבלה; התוצאה של מתן ידני, ובשלב 2 — של אישור):
```
id, org_id, user_id, resource_key,
granted_by uuid, granted_at timestamptz,
source text check (source in ('admin','request','system')),
revoked_at timestamptz null,
unique (org_id, user_id, resource_key) where revoked_at is null
```

**`permission_audit_log`** — כל שינוי-הרשאה:
```
id, org_id, actor_user_id,
action text,          -- 'restrict','unrestrict','grant','revoke', (שלב 2:) 'request','approve','deny'
target_user_id uuid null, resource_key text null,
before jsonb, after jsonb, note text, created_at timestamptz
```

### 4.3 טבלה שלב 2 (מתועדת עכשיו כדי שהמבנה יתאים — לא נבנית)

**`access_requests`** — לולאת הבקשה-אישור, כללית מספיק לשאת גם בקשת-גישה וגם בקשת-הוצאה:
```
id, org_id, requester_user_id, resource_key,
request_kind text check (request_kind in ('access','spend')),
payload jsonb,        -- להוצאה: { action, estimate_cents, params_ref, ... }
status text check (status in ('pending','approved','denied','expired')),
assignee_role text,   -- מי מאשר: 'org_admin' | 'project_manager'
assignee_user_id uuid null,
decided_by uuid, decided_at, note, created_at
```
באישור `access` → כתיבת שורה ב-`user_resource_grants` (source='request'). באישור
`spend` → הפעלה אוטומטית של הפעולה שהמתינה. **זו הסיבה** שהמבנה של שלב 1 חייב לתת
חריגות — אישור-בקשה = כתיבת חריגה; אישור-הוצאה = אותו מנגנון, kind אחר.

## 5. אכיפה

### 5.1 שרת

middleware חדש `requireResource(key)` (אחרי `requireAuth`+`requireOrg`):
1. מנהל-על, או תפקיד owner/admin בארגון → **מאושר תמיד**.
2. אחרת: `restricted = org_restrictions[key] ?? registry.defaultRestricted`.
3. אם `restricted` **ואין** `user_resource_grants` פעילה → **403 מובנה**:
   `{ error: "restricted", resource_key, request_kind: "access" }`.
4. אחרת → מאושר.

מטמון 60ש כמו `requireApp`, **עם ביטול-מטמון** בכל שינוי הגבלה/חריגה (סוגר את פער
ה-60ש של היום). ה-403 המובנה הוא מה שמאפשר לפרונט להציג "בקש גישה" (שלב 2) במקום סתם שגיאה.

### 5.2 פרונט

- הרחבת `AppAccessContext` בשדה `restrictedResources: string[]` (המפתחות שהמשתמש
  הנוכחי חסום עליהם), נפתר פעם אחת ב-`(app)/layout.tsx` לצד שאר עובדות-הגישה.
- הוק `useResourceAccess(key)` → `{ allowed, restricted }`.
- מסך/pane מוגבל → כרטיס-נעול "מוגבל — פנה למנהל הארגון" (שלב 1; שלב 2 מוסיף כפתור "בקש גישה").
- כפתור-פעולה מסוכן מוגבל → מושבת עם אותו הסבר.

הגילוי (visibility) בפרונט הוא נוחות; **האכיפה האמיתית היא ה-`requireResource` בשרת** —
מסך מוגבל גם מוחזר 403 בשרת, לא רק מוסתר.

## 6. ממשק-ניהול מאוחד

היום ההרשאות מפוזרות בשני מקומות (קונסולת `/admin` של מנהל-העל, ו-`/settings` של
הבעלים) שמנהלים תת-קבוצות שונות. המודל החדש מרכז את ניהול-ההגבלות במקום אחד:

- **מנהל-ארגון:** מסך `/settings/permissions` — שלושה חלקים:
  1. **מה מוגבל בארגון** — מתג לכל משאב בקטלוג (דלוק/כבוי).
  2. **גישות משתמשים** — לכל משתמש: הגישה האפקטיבית + מתן/שלילת חריגה ידנית.
  3. *(שלב 2)* **בקשות ממתינות** — אישור/דחייה.
- **מנהל-על:** `/admin/permissions` — תצוגת הקטלוג + ברירות-מחדל פלטפורמתיות, ויכולת
  לעשות כל מה שמנהל-ארגון עושה, בכל ארגון.

הקצאת-האפליקציות (`user_app_access`) נשארת ב-UI הקיים; המסך החדש מקשר אליו. לאורך
זמן אפשר לקפל את השניים למקום אחד — לא בשלב 1.

## 7. עשיית-סדר בקיים

- **בלבול שתי הטבלאות:** `user_app_access` (אילו אפליקציות) מול `app_user_access`
  (רמת full/lite). נשארות שתיהן (שינוי-שם ב-DB מסוכן — 250+ מיגרציות), אבל נעטפות
  בעוזרים בעלי-שם ברור בקוד + הערות, כדי שלא יתחלפו שוב.
- **באג הניקוי:** בהסרת חבר מנקים היום `user_app_access` אבל **לא** `app_user_access`
  (`server/src/modules/platform/members/routes.ts:483-488`) — מתוקן בשלב 1.
- **smrtTask בסיסי/מלא:** מגדירים בקוד את שתי הדרגות במפורש; מוודאים שהבסיסי
  (תיבה + הפריטים שלי) זמין לכל חבר-ארגון אוטומטית, והמלא = ההקצאה.

## 8. תוצרי שלב 1 (מה נבנה עכשיו)

1. **מיגרציה** (לא-הרסנית): `org_restrictions`, `user_resource_grants`,
   `permission_audit_log` + מדיניות RLS מותאמות (הקטלוג בקוד — אין טבלת `restrictable_resources`).
2. **קטלוג בקוד** `src/lib/permissions/registry.ts` — עם סט התחלתי של משאבים
   (כמה מסכים + פעולה מסוכנת אחת כרפרנס), לא ממצה.
3. **שרת:** `requireResource` + עוזר-הכרעה + ביטול-מטמון; מודול חדש
   `server/src/modules/platform/permissions/` (רשימת קטלוג, get/set הגבלות-ארגון,
   מתן/שלילת חריגה, גישה-אפקטיבית למשתמש, קריאת audit).
4. **פרונט:** הרחבת `AppAccessContext` + `useResourceAccess` + רכיב כרטיס-נעול +
   חיווט הגבלה אחת אמיתית כרפרנס.
5. **UI מאוחד:** `/settings/permissions` (מנהל-ארגון) + `/admin/permissions` (מנהל-על).
6. **smrtTask בסיסי/מלא** + תיקון באג-הניקוי.
7. **i18n** — כל מחרוזת ב-`he.json` + `en.json`.
8. **עדכון `docs/codebase-map.md`** באותו קומיט (מודול-שרת ותיקיית-רכיבים חדשים).

## 9. מה נשאר לשלב 2 (לא נבנה — המבנה כבר מתאים)

- טבלת `access_requests` + לולאת בקשה-בקליק → התראה למנהל בתיבה → אישור → כתיבת
  חריגה → התראה למשתמש.
- פעולות-הוצאה: "כוון-במקום-להריץ" → בקשת-אישור למנהל-הפרויקט → ריצה-אוטומטית לאחר אישור.
- מושג "מנהל-פרויקט" כמאשר נבדל ממנהל-הארגון (מיפוי מי-אחראי-על-מה).
