# תוכנית — אבחון אוטומטי + שני-כפתורים לתיקון האוטומטי (corrections autofix)

מצב: **טיוטה לאישור.** נכתב 2026-07-31.

## המטרה (מה המשתמש ביקש)

כשמופיע תיקון (`correction`) מסוג `code`/`ui`, ההתראה תציג — **לפני** שהמשתמש
בוחר — **מה קלוד מצא בקוד ואיך הוא מציע לתקן**, עם שני כפתורים:

1. **אישור לתיקון** → קלוד מתקן ודוחף ל-`main` **לפי כללי הדחיפה/מיזוג של הריפו**
   (בלי שער-אישור נוסף בתוך הריצה — הכפתור הוא האישור).
2. **המשך דיון** → נפתח thread אינטראקטיבי מוזרק בפרטי האבחון, וקלוד שואל איך
   להמשיך.

**שער-ביטחון (דרישת המשתמש):** אם ריצת-האבחון **לא הצליחה לרוץ**, ההתראה בכל
זאת מופיעה — עם טקסט מפורש "האבחון לא הצליח לרוץ" — כך שאף תיקון לא נעלם בשקט.

## למה זה חינם

כל ריצה כאן (אבחון + תיקון) רצה על **הקלוד המובנה** דרך ה-console runner, על
**המנוי** (`CLAUDE_CODE_OAUTH_TOKEN`, חשבון `AUTOMATION_ACCOUNT`) — **אפס טוקני
API בתשלום**, בדיוק כמו ה-triage וה-autofix היום. העלות היחידה: חלון-השימוש של
המנוי + עיכוב עד שהאבחון מוכן. לכן **אין כאן שאלת אישור-עלות**.

## מודל-הנתונים

נוסף `corrections.context.diagnosis` (JSONB על השורה הקיימת, כמו `context.triage`):

| שדה | משמעות |
|---|---|
| `status` | `pending` \| `running` \| `done` \| `failed` |
| `problem_he` | הבעיה כפי שקלוד הבין (משפט-שניים) |
| `fix_he` | הפתרון המוצע — מה ישתנה, באיזה קובץ, למה (התנהגות, לא diff) |
| `files?` | קבצים שייגעו (אופציונלי) |
| `risk?` | `low`/`med`/`high` |
| `ran_at`, `error?` | חותמת + סיבת-כשל אם נכשל |

## הזרימה

1. **טריגר** — בסוף `triage` (`triage.ts`), אם `prompt_class ∈ {code, ui}` →
   enqueue ריצת-אבחון (תור חד-משבצת כמו triage, לא חוסם את המשתמש). מסמן
   `diagnosis.status = 'running'`.
2. **ריצת-האבחון** — console run עם פרומפט **אבחון-בלבד**: חקור את הקוד, החזר
   בעיה+פתרון, **אל תשנה קוד ואל תדחוף כלום**. הריצה מפרסמת את התוצאה ל-endpoint
   מכונה חדש `POST /api/corrections/:id/diagnosis` (‏`x-cron-secret`, כמו
   `triage-sweep`) שכותב `context.diagnosis` עם `status='done'`.
3. **שער-כשל** — אם הריצה נכשלה/לא פרסמה תוך timeout → `status='failed'` (+`error`).
   סוקר ב-`jobs.ts` מסמן ריצות-אבחון תקועות. ההתראה מופיעה עם "האבחון לא הצליח
   לרוץ — אפשר להמשיך בדיון".
4. **UI** (`CorrectionsTriageReview.tsx`) — הכרטיס מציג את `diagnosis` (בעיה+פתרון)
   כשמוכן, או באנר-כשל כשנכשל. שני כפתורים:
   - **אישור לתיקון** → הזרימה הקיימת `approve` → autofix, אבל הפרומפט = "תקן
     ודחוף ל-`main` לפי כללי הריפו", **מוזרק עם האבחון** כדי לא לחקור מחדש.
   - **המשך דיון** → הקיים `continueWithClaude` → thread אינטראקטיבי מוזרק בפרטי
     האבחון + "שאל איך להמשיך".
5. **`execute.ts`** — `buildFixMessage` חוזר לגרסת "תקן + דחוף ל-`main`" (מבטלים
   את שער-הצג-ועצור-בתוך-הריצה שנוסף בטעות); מקבל את האבחון כקלט.

## קבצים שישתנו

| קובץ | שינוי |
|---|---|
| `server/.../corrections/diagnose.ts` (**חדש**) | פרומפט-האבחון + enqueue + מצב |
| `server/.../corrections/triage.ts` | hook: בסוף מיון code/ui → enqueue אבחון |
| `server/.../corrections/routes.ts` | endpoint מכונה `POST /:id/diagnosis` |
| `server/.../corrections/execute.ts` | `buildFixMessage` → fix+push; מזריק אבחון |
| `server/.../corrections/jobs.ts` | סוקר-כשל (מסמן `failed` לריצות תקועות) |
| `src/components/smrttask/log/CorrectionsTriageReview.tsx` | הצגת אבחון/כשל + שני כפתורים |
| `src/messages/{he,en}.json` | מחרוזות UI (שני הקבצים באותו commit) |

## פתוח לאישורך

1. **timeout לשער-הכשל** — הצעה: 10 דקות בלי פרסום → `failed`.
2. **"אישור לתיקון" עדיין מותנה ב-pre-push נקי** לפני הדחיפה ל-`main` (כן — זה
   נשאר השער הטכני; הכפתור מאשר את *הכוונה*, ה-build מאשר את *התקינות*).
3. האם להשאיר את הכפתורים גם כשה-autofix כבוי (`SMRTTASK_CORRECTIONS_AUTOFIX`
   dark) — או להסתיר את "אישור לתיקון" עד שהדגל דלוק.
