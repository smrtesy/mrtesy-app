# תכנון-משנה: מנטר-גישת-המתכנת (שלב 1 בהקשחת-האבטחה)

> חלק מ-`docs/security-hardening-plan.md` §5.6 / שלב 1. נכתב אחרי שכל
> חסמי-ההיתכנות אומתו חיים מול הפרודקשן (2026-08-07). מטרה: לגלות (לא למנוע)
> גישה חריגה של תפקיד-ה-DB `developer` (איימן) — מיקום חדש, נגיעה בטבלאות
> רגישות, וניסיונות-פענוח.

## מה כבר קיים ואומת (לא הנחה)

| רכיב | מצב |
|---|---|
| pgaudit על התפקיד | ✅ **פעיל** — `ALTER ROLE developer SET pgaudit.log='read, write'` הוחל ואומת. כל קריאה/כתיבה של `developer` נכנסת ליומן-Postgres שהוא לא יכול למחוק (שלב 1א — גמור) |
| מקור-לוגים תוכנתי | ✅ `GET /v1/projects/{ref}/analytics/endpoints/logs.all?sql=<BigQuery SQL>` מחזיר את `postgres_logs`. אומת. |
| IP של המתחבר | ✅ שדה `parsed.connection_from` בכל שורת-לוג |
| טקסט השאילתה + מחלקה | ✅ שורות `AUDIT: SESSION,…,READ/WRITE,SELECT,…,<SQL>` |
| ניסיון-פענוח חסום | ✅ מתועד כ-`ERROR: permission denied for function decrypt_token` / `for schema vault` |
| צינור-התראה קיים | ✅ טריגר `trg_notify_superadmins_on_error` על `log_entries` — כל שורה עם `level='error'` שולחת התראה + נכנסת לדוח-הבריאות היומי |

**המסקנה:** אין צורך לבנות צינור-התראה חדש. המנטר רק צריך למשוך לוגים, לזהות
חריגה, ו**לכתוב שורת `log_entries` עם `level='error'`** — והשאר קורה מעצמו.

## מה אפשר לזהות — ומה לא (הכנות שקובעת את התכולה)

| ליכולת | אפשרי? | איך / מדוע-לא |
|---|---|---|
| מיקום כל חיבור → מדינה + ASN | ✅ | מ-`connection_from` (IP) + חיפוש geo-IP |
| כל statement + באיזו טבלה נגע (רמת-טבלה) | ✅ | טקסט שורת ה-AUDIT |
| קריאה מול כתיבה | ✅ | pgaudit מסמן `READ`/`WRITE` |
| ניסיון להריץ פענוח / לגעת ב-vault | ✅ | שורות ה-`permission denied` |
| **משיכת-מסה מ-`source_messages`** | ⚠️ **קירוב בלבד** | pgaudit **לא** מדווח מספר-שורות-תוצאה. נזהה לפי *תדירות* (הרבה שאילתות ל-`source_messages` בחלון-זמן) או *חוסר-WHERE/LIMIT* בטקסט — היוריסטיקה, לא ספירה מדויקת |
| **גישה ל-`is_private=true` ברמת-שורה** | ❌ **לא אפשרי מ-pgaudit** | pgaudit יודע איזו *טבלה* נקראה, לא אילו *שורות*. `SELECT * FROM tasks` כולל שורות פרטיות בלי להזכיר את העמודה. נזהה רק *נגיעה בטבלה שיש בה שורות פרטיות*, לא סינון-שורות. אם צריך רמת-שורה — מנגנון נפרד (view עוטף / שכבת-אפליקציה), מחוץ לתכולה הזו |

## ארכיטקטורה — cron בבקאנד, לא pg_cron

התכנית המקורית דיברה על `pg_cron`, אבל הלוגים יושבים ב-Logflare (מחוץ ל-DB)
ונמשכים רק ב-HTTP עם טוקן-ניהול, ובנוסף דרוש חיפוש geo-IP חיצוני — שניהם נקיים
יותר בבקאנד. לכן: **job בבקאנד (Railway, `server/`)** שכבר מארח את שאר ה-cron.

זרימה כל הרצה (~5 דק'):
1. משוך מ-`postgres_logs` את שורות `user_name='developer'` מאז ה-checkpoint האחרון.
2. אסוף IP-ים חדשים → חפש מדינה+ASN (geo-IP).
3. השווה מול טבלת-בסיס (`developer_access_baseline`): IP/מדינה/ASN מוכרים?
4. פענח שורות-AUDIT: אילו טבלאות, קריאה/כתיבה, ניסיונות-פענוח.
5. על כל חריגה — כתוב `log_entries(level, category, message, metadata)`; הטריגר הקיים שולח התראה.
6. עדכן checkpoint + טבלת-הבסיס.

## רכיבים לבנייה

1. **טבלת-בסיס** `developer_access_baseline` — IP-ים/מדינות/ASN-ים שכבר נראו + חותמת.
2. **checkpoint** — חותמת-הזמן האחרונה שעובדה (טבלה קטנה או `sync_state`).
3. **מקור geo-IP** — IP → מדינה + ASN (ראה הכרעה א').
4. **ה-job** — מודול ב-`server/src/modules/…` + רישום ב-cron.
5. **טוקן** — ה-job צריך `SUPABASE_ACCESS_TOKEN` (PAT ניהולי) לקריאת הלוגים — לאחסן ב-Railway env / managed-secrets.

## ספים והתנהגות (לפי הכרעותיך)

| אירוע | תגובה |
|---|---|
| IP חדש **בתוך** מדינת-הבסיס (הודו) | לוג בלבד (מוסיף לבסיס, בלי התראה) |
| **מדינה חדשה** או **ASN חדש** | 🔴 התראה מיידית |
| נגיעה ב-`user_credentials` / `app_secrets` | 🔴 התראה |
| ניסיון `decrypt_token` / `vault` (גם אם נחסם) | 🔴 התראה |
| קירוב משיכת-מסה מ-`source_messages` (תדירות/חוסר-WHERE מעל סף) | 🟠 התראה (ראה הכרעה ד') |

## הכרעות פתוחות למנהל

- **א' — מקור geo-IP:** (1) שירות חיצוני כמו `ipinfo.io` — שכבה חינמית ~50K/חודש
  מספיקה בגדול (חיבורי איימן מעטים), נותן מדינה+ASN, אך תלות חיצונית וסוד-API;
  (2) קובץ GeoLite2 מקומי — בלי תלות/עלות, אך צריך לעדכן אותו מדי פעם וה-ASN שם
  פחות עשיר. **המלצה:** ipinfo בשכבה החינמית — פשוט ומדויק; אפס עלות בהיקף הזה.
- **ב' — תדירות/מיידיות:** cron כל 5 דק' = "כמעט-מיידי" (עד 5 דק' עיכוב). מיידיות
  אמיתית דורשת Log Drain (webhook) של Supabase — יותר הקמה. **המלצה:** cron 5 דק'.
- **ג' — `is_private` ברמת-שורה:** לא אפשרי מ-pgaudit. לוותר (נסתפק בנגיעה
  ברמת-טבלה), או לבנות מנגנון נפרד בהמשך. **המלצה:** לוותר בשלב הזה.
- **ד' — סף משיכת-מסה:** כמה שאילתות `source_messages` בחלון-זמן נחשבות חריגה?
  ברירת-מחדל מוצעת: מעל ~20 שאילתות ב-10 דק', או כל `SELECT` בלי `WHERE`.

## שלבי-בנייה (אחרי אישור ההכרעות)

1. מיגרציה: `developer_access_baseline` + checkpoint (תוספתי).
2. מודול ה-job בבקאנד + פענוח שורות-AUDIT + חיפוש geo-IP.
3. רישום ב-cron (כל 5 דק').
4. אימות חי: להתחבר כ-`developer` ממדינה "חדשה" (או לזייף IP בבדיקה) ולוודא
   שנכתבת `log_entries` והתראה יוצאת; לוודא ש-IP מוכר בהודו לא מתריע.
